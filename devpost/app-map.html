Then the settlement changes

simulation.ts advances ten-second ticks. It assigns homes/jobs, produces and consumes goods, handles hunger/illness, arrivals, festivals, tourists, merchants and cargo schedules. Derived statistics drive the management screens and world activity.

Homes and jobs refer to building instance IDs, so repeated copies remain independent. Outposts open more local ground; each completed bridge adds an islet.

Keep each layer responsible

catalog.ts defines sixteen recipes, roles, tiers, designs and stages. bridge.ts carries a read-only frame plus player commands. Rendering never awards supplies or advances production independently.

settlement.css handles desktop management and mobile Build/Village screens. The existing runner keeps its own styles and controls.

A design practice to reuse

The road revision showed that mathematical alignment does not guarantee readable motion. Connect player feedback to a concrete constraint: road width, foliage exclusion, pickup depth, or time-to-contact. Then verify that constraint in code and retry it in motion.

For a settlement change, follow the same route: say what the player should notice, locate the state transition, trace the visible feedback, and test resource/save consequences. Controller tests, simulation tests and placement tests show examples.
